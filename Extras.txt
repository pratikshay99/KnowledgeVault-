Shallow copy Vs Deep copy:
Feature			Shallow Copy						Deep Copy
What it copies		Only top-level object, not nested objects			Top-level + nested objects also cloned
Object references	Copies object references, not actual nested objects		Creates new copies of all nested objects
Default in clone()?			✅ Yes																  ❌ No (must be implemented manually)
Performance		Faster, less memory usage					Slower, more memory (but safer)
Use case			When object is immutable or inner objects won’t change	When complete independence from original is required

In shallow copy:
-p1 and p2 are two different Person objects ✅
-But they both reference the same Address object inside ❌
e.g
Person p1 = new Person("John", new Address("Delhi"));
Person p2 = p1.clone(); // shallow copy

System.out.println(p1 == p2); // ❌ false – different Person objects
System.out.println(p1.address == p2.address); // ✅ true – same Address object
💡 Why?
Because super.clone() creates a new object (i.e., a new Person), but does a bitwise copy of fields.

Primitive fields (like int, boolean) → values are copied.

Object references (like Address) → reference is copied, not the object.

So now both p1.address and p2.address point to the same Address.

Part	Shallow Copy	Deep Copy
p1 == p2	false (different Person objects)	false
p1.address == p2.address	true (same inner object)	false (inner object also cloned)
💡 Analogy:
Shallow Copy = Copying a document with a link to a file.
Deep Copy = Copying a document and also duplicating the actual file.
🔥Default clone() in Java does shallow copy. For deep cloning, you must manually clone nested objects, or use serialization or third-party libraries.

1️⃣ Does clone() call the constructor?
❌ No!
It creates a new object without invoking any constructor.
super.clone() performs a bitwise memory copy (shallow copy).

    public A clone() throws CloneNotSupportedException {
        return (A) super.clone();
    }
}

A a1 = new A();
A a2 = a1.clone();
a2.arr[0] = 99;
System.out.println(a1.arr[0]);
✅ Output: 99
Because the array is shared between a1 and a2 → shallow copy.
3️⃣ Can clone() be used for deep copy?
✅ Yes — but only if you manually override clone() to also clone all nested objects.

5️⃣ What are alternatives to clone()?
-Copy constructors
-Serialization (deep copy)
-3rd party libraries (Apache Commons SerializationUtils.clone())

⚠️ Why clone() is not recommended in modern Java?
-It breaks encapsulation (Object class knows internals of all subclasses)
-Not flexible — doesn’t work well with final fields, immutable design
-Easy to mess up shallow vs deep copy
✅ Instead, Java devs prefer:
-Copy constructors
-Factory methods
-Builder pattern

🔐 Thread-Safety: ❌ ArrayList is not thread-safe.
❌ Problem:
-If multiple threads modify a normal ArrayList at the same time, you may get:
-ConcurrentModificationException
-Data inconsistency
-Unexpected results
✅ Solution 1: Use Collections.synchronizedList(...): Wrap the list to make it synchronized.
✅ Solution 2: Use CopyOnWriteArrayList

 ✅ 1. Collections.synchronizedList(...) 📌 Use when:
     -You want to share a list between threads
     -You need frequent writes/modifications
     -You don’t mind using synchronized blocks during iteration
 ⚠️ BUT:
    -You must manually synchronize during iteration to avoid ConcurrentModificationException
 
 ✅ 2. CopyOnWriteArrayList: 📌 Use when:
    -Your app is read-heavy, write-light
    -You want safe iteration without any locking
    -You want to avoid manual synchronized blocks
 ⚠️ BUT:
   -Each write creates a new copy → memory & performance cost
    -Avoid if frequent add/remove
 
 ✅ 3. Iterator with iterator().remove()📌 Use when:
    -You’re looping through any collection
    -You want to remove elements while iterating
 ⚠️ Don’t use list.remove(...) inside for-each

Uniqueness Guarantee:
-You cannot store the same element twice.
-Equality is checked using equals() method (for logical equality).
Order is not guaranteed (depends on implementation)

when to use: to prevent duplicates, to model a mathematical set (like union, intersection, etc.),to test membership efficiently.

🔸 Set vs Collection
Even though Set extends Collection, it strengthens the contract:
-Collection allows duplicates.
-Set prohibits duplicates.
So, it's like a specialized Collection designed purely for uniqueness.
🧠 Conceptual Depth: What Makes an Element "Duplicate"?
-A Set relies on logical equality(.equals()), not reference equality(=).
-So two different objects with the same content (as defined by equals()) are considered duplicates.

Map: 
-not a subtype of the Collection interface(separate hierarchy in the Java Collections Framework)
-Storing key-value pairs, where each key maps to exactly one value,Keys are unique, values can be duplicated.
-No duplicate keys: Adding a key that already exists will overwrite its value.
-One null key & Multiple null values are allowed.
-If you want to preserve order, use LinkedHashMap, other type of Map doen't follow insertion order.
-map.put("name", "Alice");
map.put("name", "Bob"); // Key "name" not duplicated, only replaced
e.g real-world dictionary:
look up a word (key), &  get its definition (value), can’t have same word defined twice, But multiple words can have same definition.
✅ Use entrySet() when:
You need both the key and the value in your loop.
✅ Use keySet() when:
You only need keys and don't care about values.

Without equals() and hashCode(), the map will treat them as different keys — big mistake!
Map<Person, String> people = new HashMap<>();
people.put(new Person("101"), "Alice");
people.put(new Person("101"), "Bob"); // Overwrites because equals() returns true

❓ “Why would you prefer entrySet() over keySet() when iterating a Map?”
- prefer entrySet() when I need both the key and value during iteration, because it avoids the overhead of calling get(key) for each key.
-With keySet(), accessing values requires an extra lookup (map.get(key)), which can be inefficient — especially for large maps or maps with slower lookup times like TreeMap.
-entrySet() gives direct access to the key-value pair in a single step, making it more efficient and cleaner.
💡 Also, in concurrent or synchronized maps, using entrySet() minimizes the chance of race conditions, since there's no separate get() call — everything is accessed atomically from the entry.
💡 Tricky Notes
-get("unknown") returns null, but you can't tell if it's a missing key or a key mapped to null. Use containsKey() to confirm.
-entrySet() gives full control over both key and value while iterating.
-Mutating the key object after insertion (if using custom objects as keys) will break the map.

LinkedHashMap | ✅ Yes | Maintains insertion order
TreeMap                 | ❌ No | Orders by key (sorted)
ConcurrentHashMap       | ❌ No | Focused on concurrency
